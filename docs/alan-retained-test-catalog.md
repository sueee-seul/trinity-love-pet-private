# Alan-owned retained test catalog

This document records only tests that are worth keeping long term. It is not a complete test-file inventory or a deletion-candidate list.

Tests that only supported one product implementation, locked a one-time copy/layout decision, validated a mock placeholder, or have no continuing contract, business-rule, security, persistence, integration, or regression value are intentionally omitted.

Mixed-author files are handled at test-declaration level. A test is included only when its declaration is attributed to Alan. Current working-tree changes are marked `WIP`; they are included only when they protect an active contract and are not treated as old one-time tests.

The catalog is based on static source, test, configuration, and Git inspection. It does not claim that the tests currently pass. Mocked PostgreSQL, provider, model, fetch, and browser dependencies are identified as mocks; they are not evidence of live service behavior.

## Test-level tags

| Tag           | Meaning                                                                                                                                      |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `unit`        | Isolated business rule, mapper, selector, component, hook, store, schema, or helper behavior.                                                |
| `API`         | Verifies an HTTP request/response, route validation, authentication boundary, or API transport mapping.                                      |
| `integration` | Crosses multiple modules, a service/repository boundary, a model/tool boundary, a database boundary, or a package contract.                  |
| `smoke`       | Verifies a minimal critical runtime path, startup/dependency path, or live adapter path. It is not added merely because a test is important. |
| `browser E2E` | Uses the real browser flow and user-visible navigation/state.                                                                                |

Tags can be combined. For example, `API + integration` means that the test is an API test and also crosses a real or test-isolated integration boundary.

## How to read the catalog

Every named test item below has four required explanations:

1. what it tests;
2. the expected behavior;
3. why the behavior needs a test;
4. why the test is important to keep.

Items are grouped in one row only when they protect the same boundary and have the same reason for retention. The exact test names remain listed so each retained item can be located.
